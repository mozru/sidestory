# Security

## Reporting a vulnerability

Please report security problems privately to the maintainer ([email removed]) rather than in a public issue. Include a minimal explainer or repository that reproduces the problem. You'll get an acknowledgement within a few days.

## Threat model

Code Explainer renders files from the repository you open. Those files may come from anyone: a cloned project, a pull request branch, a teammate. The extension treats everything under `.explain/`, every file an anchor points at, and every asset an explainer references as **untrusted input**. It runs in Restricted Mode (untrusted workspaces) because, there, it never executes anything from the repository. The one exception, interactive widgets, is opt-in and described in its own section below.

What an explainer can do: show HTML and CSS in the panel, with images, fonts and stylesheets from its own folder; ask the editor to show and highlight lines of files inside the repository; offer links that you click.

What it can't do, and how that is enforced:

| Concern | Protection |
|---|---|
| Running script | Explainer content renders in an iframe sandboxed without `allow-scripts`, under a CSP that allows only the panel's own script (by nonce). Event handlers, `<script>`, `javascript:` URLs, SVG script and animation are also stripped. |
| Covering or faking the panel's controls | Content is confined to the iframe's box, including the browser top layer (dialogs, popovers, select pickers). |
| Reaching the network | CSP `default-src 'none'`; no `connect-src`; remote images, fonts, stylesheets and `@import` are dropped. |
| Reading files outside the repo | Manifest paths must be canonical repo-relative paths (no `..`, absolute, drive, UNC, URL, glob or control characters; no `.git`). Files are read only after following symlinks and confirming the real path is inside the repo; assets only inside the explainer's own folder, of allowed types and sizes. |
| Leaking local paths or reaching local services through links | External links open only for public `http(s)`/`mailto` URLs without credentials; `localhost`, `*.local`, private, loopback and link-local addresses are refused (on a remote host VS Code would tunnel them). Links to other explainer files open inside VS Code. |
| Exhausting CPU or memory | Size limits on manifests (1 MB), HTML (5 MB), code files (10 MB), assets (5 MB each, 20 MB per panel); limits on anchor counts, quote sizes and identifier lists; anchor resolution runs with a per-anchor work budget and yields between anchors. |
| Abusing the webview ↔ extension channel | Every message from the panel is validated against a schema; anchor ids, paths and URLs are re-checked by the extension. |

## Known limits

- `localResourceRoots` includes the `.explain/` folder (a panel can move between the explainers in it). VS Code checks resource paths by prefix, not by real path, so a symlink inside `.explain/` could in principle expose another readable file to the panel's own resource loader. Explainer content itself can't load such URLs (assets go through the extension, which checks real paths), and the panel can't send data anywhere.
- Explainer HTML can't run script. Code from the repository runs only as widgets, below.

## Interactive widgets

Widgets are React components in an explainer's folder (`<explain-widget src="widgets/x.tsx">`). Unlike the rest of an explainer, **they are code from the repository, and they run.** The boundary is your informed consent plus limits on what a widget can see; the sandbox makes misuse harder but is not treated as containment.

### When widgets run

- Never in Restricted Mode (an untrusted workspace), and never while the `codeExplainer.widgets.enabled` setting is off. The setting is application-scoped: a repository's `.vscode/settings.json` can't turn it on.
- Only after you agree in a **native VS Code dialog** (not in the panel, whose content the explainer controls). It names the explainer and its changed files, and says that widgets can read the code the explainer points at, including unsaved edits, and may be able to reach the network (their usual network calls fail, but the sandbox is best effort, below). When the widgets would also read anchors whose quotes nobody confirmed, the same dialog lists those files and line ranges and offers to allow both at once; "Run Widgets" alone allows only running.
- Each explainer asks the first time its widgets would run in a workspace, with or without git (an explainer copied or unzipped into a workspace you trusted doesn't run on another explainer's consent).
- Consent is kept per workspace (VS Code's workspace storage; in browser VS Code that storage is per browser profile), with a hash of every file each explainer's widgets load (code, JSON, images) and the blob git had for it at HEAD. The last 16 versions of each file you agreed to (or edited) are remembered with their git blob, so checking out a branch you already agreed to doesn't ask again; the same bytes under another blob still do. You're asked again when widget code changes after git's own version of that file changed (a checkout, pull, merge or rebase), whatever the working-tree bytes look like (line-ending conversion, checkout filters such as `ident` or LFS, encodings), and for widget files you never agreed to that git has (another explainer's widgets after a clone or pull). The decision waits until git has finished (no index lock, no merge or rebase in progress) and for a status refresh made after the change. You're always asked about changed code when the folder is in a git repository VS Code's git extension doesn't know, when git doesn't settle, or when a widget file is reached through a symlink anywhere below the repository root (the file, a folder, the explainer folder or `.explain` itself). Edits in the working tree, by you or by any tool, are treated as yours and don't re-ask. **Code Explainer: Revoke Widget Consent** clears it, together with the anchors you let widgets read.
- All of this is enforced by the extension host: the panel gets no compiled code, libraries or file contents for widgets without trust, the setting and consent.

### What a widget can reach

- **Its own frame.** Each widget runs in an `<iframe sandbox="allow-scripts">` with an opaque origin, created by the panel and laid over the explainer. It can't reach the panel's document, VS Code, other widgets, the file system or VS Code's resource URLs. The frame's CSP allows only the bootstrap script (by hash) and what it loads, inline styles, and `data:`/`blob:` images, fonts and media; `eval`, popups, dialogs, form submission and navigation of other frames are blocked. `fetch`, XHR, WebSocket, EventSource and `sendBeacon` are replaced with stubs that refuse, and WebRTC constructors and `<link rel=prefetch|preconnect|dns-prefetch|prerender|modulepreload>` are removed inside the frame. That last hardening is best effort: a widget can create a scriptless child frame whose constructors are unpatched.
- **Code, only when its author demonstrably knew it.** `useAnchorCode` returns an anchor's code only when the anchor's pinned quote (whitespace-normalized, case-sensitive) is committed in git or was confirmed by you in VS Code, the code matches it in full (or, for files tracked by git, the quote matches the committed version and the differences are working-tree edits), the file isn't ignored by git, isn't secret-looking (below), and is at most 2,000 lines. Git state comes from VS Code's git extension; the extension never runs git itself. Git is asked about the file the code is read from (behind any symlink). A widget gets the code only of anchors it names in a direct `useAnchorCode('id')` call (any anchor when the id is computed or the function is used any other way), however it asks. Pinning anchors that widgets read asks you first (a native dialog listing the files and line ranges), unless the quote stays as it is committed; the standalone checker refuses to pin them unless given `--yes-widgets-may-read`.
- **Files it imports** from the explainer folder only (real paths checked, sizes capped, the same secret-file names refused). Each widget gets only its own props, state and code.
- **Secret-looking files, never.** No widget gets a file whose *name* looks like it holds secrets: not through `useAnchorCode`, not as an import or image. The rule is judged on the file name (the last path segment), case-insensitively, against both the path the explainer names and the real file behind any symlink; folder names don't count. Secret-looking, whatever the extension: `.env`, `.env.*`, `.envrc`; `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.keystore`, `*.jks`, `*.tfvars`; names containing `kubeconfig`; `id_rsa`, `id_dsa`, `id_ecdsa`, `id_ed25519` and their `.pub`; `.npmrc`, `.netrc`, `.pypirc`, `.git-credentials`, `.dockercfg`, `.htpasswd`; `appsettings.*.json`. Secret-looking only for config and data files (extension `json`, `yaml`, `yml`, `toml`, `ini`, `env`, `conf`, `cfg`, `properties`, `xml`, `txt`, or none): names containing `secret`, `credential`, `password`, `token`, `apikey` (also `api-key`, `api_key`), or `.local.` (`settings.local.json`). Source files (`.ts`, `.tsx`, `.js`, `.py`, `.sv`, `.go` and every other extension) are never secret by name, so `src/tokenBucket.ts` or `src/tokens/lexer.ts` can be read like any code; a secret kept in a source file, or in a file not on this list, is protected only by the other rules (the quote must be author knowledge, ignored files are never served, and you consent to the widgets).
- **The editor, within limits.** A widget can highlight lines inside the current step's code without a click. Showing code, changing steps and moving focus need a click or key press in that widget, checked by the panel when the request arrives (user activation, the widget's frame holding focus, and no gesture of the panel's own that pointed elsewhere). Only the part of a widget you can see counts as where the pointer pointed. A widget's frame never extends past its placeholder, whose size author CSS can't change, and the panel draws the "Interactive" label over a running widget itself, outside the explainer's content, so author CSS can't hide it. Requests are schema-checked, size-capped and rate-limited.
- **Resources.** Widget code is compiled in a worker thread with time and memory limits. In the frame, loops are guarded (stopped after about 1 s without yielding), a watchdog unmounts and disables a widget that stops answering, and at most 8 widgets are mounted at once (24 per explainer). The watchdog acts on the panel's own evidence (pongs missing while the panel's timers run on time; heartbeats that come back late by the panel's clock, or stay missing for 20 s) and never while one of the extension's dialogs is open or for 5 s after (VS Code holds a webview's messages back behind its dialogs). A widget it turned off offers **Try again** in its box, which counts toward stopping the explainer's widgets (a third hang within 5 minutes stops them until **Code Explainer: Enable Widgets**).
- **Focus.** A widget never gets focus without your interaction: focus that arrives without evidence of your click or key press in that widget is given back, every time. A widget that keeps doing it is stopped after three attempts the panel is sure of; its box offers **Restart widget**. Attempts the panel isn't sure of aren't counted: the pointer resting on the widget, or the widget's frame reporting a pointer or key press of its own at that moment (an instant click by automation or assistive technology, which shows the panel no pointer travel). That report comes from the widget's frame, so a hostile widget can make itself exempt from being stopped this way, but not from having focus taken back; focus pulled from outside the webview (the editor) always counts.
- **Stored data.** What readers set in widgets (`useWidgetState`, at most 64 KB per widget and 256 KB per explainer, 16 explainers) is kept in the workspace storage of VS Code, as the panel's own state is; it holds only what widget code chose to save.

### Accepted risks

These are known and accepted; they are why running widgets needs your consent.

- **Widgets may reach the network.** WebRTC, prefetch-style links and future browser features can get past the frame's CSP; the hardening above reduces casual misuse but isn't complete. Treat anything a widget can see (its props, its state, the code `useAnchorCode` gives it) as something it could send out.
- **Deceptive UI inside the widget's box.** A widget can draw anything in its box, which the panel frames and labels "Interactive", including a fake cursor drawn while the real pointer is inside it.
- **Clipboard writes and drag-out data** after a click in the widget (pastejacking): check what you paste.
- **Focus theft from the editor.** A widget that takes focus without a click can receive up to about 200 ms of keystrokes before the panel notices and gives focus back.
- **Pointer-based allowances.** Within about 5 s of pressing J or clicking a panel control, a widget the pointer moves toward (or across, on the way out of the panel) can navigate or take focus; refusing it would break "press J, then click the widget that came up". So can a widget the pointer was already resting on, or had just moved into (heading in, within about 24 px of its edge), when a key was pressed in the panel; not one that moved or grew under a pointer resting elsewhere.
- **Between widgets.** A widget can take focus within about 5 s of a click inside another widget: the panel sees neither click.
- **Touch.** With no pointer samples, a tap on the prose followed within about 5 s by a tap on a widget is refused; tap again.
- **Fast moves.** After a fast pointer move into a widget and a key press in the panel, a click in that widget within about 5 s may be refused (focus returns to its placeholder); click again. It never counts against the widget.
- **Refocus target.** After a focus theft, focus returns to the active editor group, even if it was taken from the terminal or the sidebar.
- **Keyboard.** Escape and Tab are seen by widget code first, so a widget can hold keyboard focus until you click elsewhere. VS Code shortcuts don't work while focus is in a widget.
- **Side channels** between widgets and the panel in the shared renderer process (timing, memory pressure).
- **Unsaved edits.** `useAnchorCode` serves the live text of a resolved anchor, unsaved edits included (the consent dialog says so).
- **Consent follows the working tree.** Widget code changed by any tool, including other extensions or agents writing files, counts as your own edit and doesn't re-ask. Code that arrives without HEAD moving (`git checkout <rev> -- path`, `git restore --source`, `git apply` of a pull request's diff, `git stash pop`) doesn't re-ask either, once the explainer's widgets have run here; a whole explainer copied or unzipped in asks the first time. Without git, changes to an explainer you agreed to don't ask again. The limits on what widgets can see apply regardless.
- **Panel origin.** The panel accepts host messages only from its own origin, which relies on that origin being shared only by this extension's panels, which run only its own script.
- **Hangs.** A widget that hangs freezes the other widgets (they share one process). Where sandboxed frames aren't isolated in their own process, it also freezes the panel, and in a browser without site isolation (possible when VS Code runs in a browser) the whole VS Code tab, until the watchdog disposes the panel and recreates it with that widget disabled. VS Code desktop keeps site isolation on, so there a runaway widget can't freeze the window.
