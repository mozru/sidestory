# Security

## Reporting a vulnerability

Please report security problems privately through GitHub's private vulnerability reporting (https://github.com/mozru/sidestory/security/advisories/new) rather than in a public issue. Include a minimal sidestory or repository that reproduces the problem. You'll get an acknowledgement within a few days.

## Threat model

Sidestory renders files from the repository you open. Those files may come from anyone: a cloned project, a pull request branch, a teammate. The extension treats everything under `.sidestory/`, every file an anchor points at, and every asset a sidestory references as **untrusted input**. It runs in Restricted Mode (untrusted workspaces) because, there, it never executes anything from the repository. The one exception, interactive widgets, is opt-in and described in its own section below.

What a sidestory can do: show HTML and CSS in the panel, with images, fonts and stylesheets from its own folder; ask the editor to show and highlight lines of files inside the repository; offer links that you click.

What it can't do, and how that is enforced:

| Concern | Protection |
|---|---|
| Running script | Sidestory content renders in an iframe sandboxed without `allow-scripts`, under a CSP that allows only the panel's own script (by nonce). Event handlers, `<script>`, `javascript:` URLs, SVG script and animation are also stripped. |
| Covering or faking the panel's controls | Content is confined to the iframe's box, including the browser top layer (dialogs, popovers, select pickers). |
| Opening code without the reader asking | Links to code (`data-explain-ref`, `data-explain-code`) are opened only by the panel's own handlers, for a trusted click on the link or Enter (not Space, not a held key) on a link the reader tabbed to or pressed; focus that arrives any other way (an in-page link, a dialog, a widget giving focus back) doesn't count. The content runs no script, and widgets can't reach the handlers. `accesskey`, `autofocus` and invoker commands (`command`, `commandfor`, `interestfor`) are stripped, links on or around form controls and widgets are ignored (a `<label>` forwards clicks to its control), and attributes starting with `data-cx-` are stripped, so the panel's own markers can't be forged. The extension checks `data-explain-code` again as a backstop: identical requests within 300 ms count once and at most 10 a second are acted on (before any file is touched), the path must be inside the repository after following symlinks with no `.git` segment, and a file with a secret-looking name (the link's or the real file's) opens only after the reader confirms. Cursor lighting reads only documents already open, and asks a language for symbols only in those. |
| Reaching the network | CSP `default-src 'none'`; no `connect-src`; remote images, fonts, stylesheets and `@import` are dropped. |
| Reading files outside the repo | Manifest paths must be canonical repo-relative paths (no `..`, absolute, drive, UNC, URL, glob or control characters; no `.git`). Files are read only after following symlinks and confirming the real path is inside the repo; assets only inside the sidestory's own folder, of allowed types and sizes. |
| Leaking local paths or reaching local services through links | External links open only for public `http(s)`/`mailto` URLs without credentials; `localhost`, `*.local`, private, loopback and link-local addresses are refused (on a remote host VS Code would tunnel them). Links to other sidestory files open inside VS Code. |
| Exhausting CPU or memory | Size limits on manifests (1 MB), HTML (5 MB), code files (10 MB), assets (5 MB each, 20 MB per panel); limits on anchor counts, quote sizes and identifier lists; anchor resolution runs with a per-anchor work budget and yields between anchors. |
| Smuggling content through code block highlighting | The extension host tokenizes code blocks with grammars shipped in the extension, in a worker thread with time and memory limits (a block that takes too long stays plain; repeated timeouts turn highlighting off for that panel). The panel gets back only lengths and colors: it cuts its own text with them and builds the spans itself, as text, so code that looks like HTML stays text. Languages come from a fixed list; colors are validated hex values from the reader's installed color theme and the `editor.tokenColorCustomizations` setting, which a repository's workspace settings can also set (hex colors and known font styles only, at most 2,000 rules, scopes of at most 1,000 characters, theme-name patterns matched in linear time). |
| Spoofing in native UI (sidebar, CodeLens, status bar, pickers, notifications) | Repository text (titles, summaries, step titles, group and folder names) is shown as plain text: control, bidirectional, invisible and tag characters are removed and lengths are capped when it is indexed; icon syntax (`$(…)`) is escaped where VS Code would render it, link syntax is broken in notifications, and tooltips are plain strings (no markdown, links or commands). Commands carry only arguments the extension built and validated (`sidestory.openAt` re-checks the folder, names and anchor id). The workspace index only reads and is bounded in every mode: at most 5,000 sidestories, 100,000 anchors and steps, 2,000 anchors per file, byte and time budgets per batch, and a linear HTML scanner with a time backstop. |
| Abusing the webview ↔ extension channel | Every message from the panel is validated against a schema; anchor ids, paths and URLs are re-checked by the extension. |

## Known limits

- `localResourceRoots` includes the `.sidestory/` folder (a panel can move between the sidestories in it). VS Code checks resource paths by prefix, not by real path, so a symlink inside `.sidestory/` could in principle expose another readable file to the panel's own resource loader. Sidestory content itself can't load such URLs (assets go through the extension, which checks real paths), and the panel can't send data anywhere.
- Sidestory HTML can't run script. Code from the repository runs only as widgets, below.

## Branch coverage and git

- **The extension never runs git itself.** Branch coverage (the file decorations, This File, the "This branch" group, the Next/Previous Unexplained Change commands) comes from one comparison service that reads the branch's merge diff and the files' versions through VS Code's git extension (its API), which runs only in trusted workspaces, with your git settings. In Restricted Mode nothing is read. Changes and coverage are computed by the extension's own code (the same as the checker's), not by a diff tool.
- **Old versions of files come from git objects, never the file system.** The left side of a step's diff, and base-side anchors, are read-only `sidestory-git:` documents naming a full commit id, a repository by a salted hash (no path), and a repo-relative path. The provider serves regular files only (symlinks, submodules and folders are refused, so nothing outside that commit's tree is followed) and nothing can be written through it. Files over 10 MB are refused, before and after the read.
- **Repository text stays text.** Paths with control characters, a backslash, `..` or `.git` segments or a leading `:` are never read, decorated or opened. Windows device names (`con`, `nul.txt`), segments ending in a dot or a space, and a `:` anywhere (an NTFS alternate data stream) are read only from git objects by id, never from the disk (one module, `src/core/repo-path.ts`, with the checker); paths, branch, tag and commit names are cleaned before they are shown, and shown literally in quick picks. Refs reach the git extension only as validated, fully qualified names (`refs/heads/main`) or full commit ids: a sidestory's `base` and **Sidestory: Set Base…** pass §3.1's grammar first, and its "Commit…" entry must be hex.
- **No network.** Sidestory never fetches. In a partial clone it reads only objects you already have; the git extension's own rename detection when it lists changes, and reopening an old version, can still download the objects they read.
- **Your git configuration applies** as in any diff the git extension shows you (for example diff drivers or textconv it uses when reading a version); coverage counts the bytes it is given.
- **Nothing a branch changes slips past coverage by not being text.** A binary file, a symbolic link, a submodule, a type change (a file becoming a link, say) and a path Sidestory refuses each count as one change that only a `trivialFiles` match can mark, in the extension and the checker alike; a branch can't hide code from the CI gate by committing it as a link or under a name that isn't read. Only a sidestory's own `manifest.json` and `sidestory.html` (in a folder that is a complete sidestory), and its shared comments' event files (exactly `threads/t_<ULID>/e_<ULID>.json` there: JSON data, never run), are left out: any other file under `.sidestory/` counts, so code can't hide there and be required from elsewhere; a rename from code onto a sidestory's own file counts as a deletion; anything under `.sidestory/archive/` counts as one change, except a landed sidestory's files moved there unchanged when it is archived in a branch (its `manifest.json` only as the archive job rewrites it: a valid manifest equal to the old one but for `base`, `head` and `landed`, each checked: `base` the old base or a full commit id, `head` a full commit id, `landed` only the archive job's own fields). A Git LFS file whose pointer changed counts as one change too, so a `.gitattributes` line can't move scripts out of review; a file that only starts with the pointer's version line is compared as text. **Moves count:** files renamed or copied across folders, edited or not, make one move change per moved prefix (moving `src/auth.js` to `src/disabled/auth.js` can switch it off), renames within one folder group only when they share a transform of the name (`*.js → *.ts`), and a rename that can switch a file off (an added `.disabled`, `.bak`, `.off`, `.orig`, `.old` or `~`, or code renamed to a non-code extension) is never grouped, so `auth.ts → auth.ts.disabled` never hides among them. A step that resolves in one of the moved files explains a group; a trivial mark or `trivialFiles` match covers only its own file's move, so one mark on a README can't hide a moved `auth.js`. Every report of a move lists its files. Only mode-only changes and `\r\n` ↔ `\n` changes are left out; a lone CR turning into a newline is a real change.
- **Memory is bounded by bytes:** diffs kept between recomputes take at most about 64 MB, and merge-base versions another 64 MB, whatever the number of files; in working tree mode a file keeps one cached diff, replaced when its content changes.

## The checker and git

The standalone checker (`dist/check.cjs`) runs git itself for `--coverage` and for pinning a sidestory with a base: there is no git extension in a terminal or CI. The repository it reads may be hostile (a pull request in CI, a project you just cloned), and an agent may run it, so:

- **It finds git itself**, on `PATH`, in JS: only absolute entries outside the repository count (`.`, empty entries and folders inside the checkout are skipped), and on Windows only `git.exe` or `git.com`. It then runs that file by its full path, so a `git` or `git.exe` committed to the repository never runs (Windows would otherwise look in the current folder, the repository's root, first). `NoDefaultCurrentDirectoryInExePath` is set for whatever git starts in turn.
- **It finds the repository itself**, as the nearest folder above the sidestory (or `--repo`) with a `.git` entry, and always tells git which one (`--git-dir`, `--work-tree`). The first `.git` decides: a directory, a link to one, or a file whose `gitdir:` names one; anything else there means no repository, never a search further up. A bare repository planted inside the tree, with a config that would run commands, is never discovered or read.
- **It never uses a shell**, and gives git a clean environment: inherited `GIT_*` variables (as a hook calling it might set) are removed, prompts and optional locks are off, replace refs (`refs/replace/`, which could make one object read as another) are ignored, and every call turns off the pager, fsmonitor, hooks, commit signature checks, external diff tools, textconv and all network access. Network access is off through `GIT_ALLOW_PROTOCOL=none`, which no configuration overrides: `protocol.allow=never` alone isn't enough, because a repository's own `protocol.ext.allow=always` (per protocol) wins over it, and `ext::` transports run commands. Each call is killed after 120 seconds. In a partial clone a missing object is reported, never fetched.
- **No clean filter runs.** Committed changes (`--committed`, `--head`, CI) are listed tree to tree and file contents read with `cat-file`, which run no filters. Comparing the working tree, git may refresh files through a clean filter that `.gitattributes` selects; on git 2.40 or newer the checker replaces the repository's attributes with empty ones, and on older git it refuses working tree mode when a filter other than git-lfs's standard one is configured (use `--committed` or a newer git). It refuses too when `.git/info/attributes` selects a filter (for a linked worktree, its own and the main repository's). Submodules are never looked into: the working tree diff ignores their working trees, and a submodule's commit changed on the branch or staged is read from the index (`--cached`).
- **Refs and paths are data.** Paths from git's output with control characters, a backslash, `..`, `.git` or a leading `:` are never read; each counts as one change (a warning names the rule it breaks) that only `trivialFiles` can mark. Paths Windows would read differently (device names like `con` or `nul.txt`, segments ending in a dot or a space, a `:` anywhere) are read by blob id only, never from the disk: in working tree mode such a file counts as one change too. A `base` from a manifest or `--base` must pass the same grammar as in the extension (no leading `-`, no `..`, `@{` or pseudo-refs like `HEAD`) before git sees it, is resolved through fully qualified names (`refs/heads/main`, then its upstream, `refs/remotes/…`, `refs/tags/…`), and only full commit ids are used afterwards. Paths come after `--` as literal paths, and only hex object ids are ever written to git's input.
- **Sizes are capped:** 10 MB per file and 200 MB per run, checked before reading, and a blob batch is held once in memory, not as chunks plus a copy; working tree files are read only when they are regular files inside the repository (no links, no FIFOs). A link, a folder (a submodule or a nested repository) or anything else there counts as one change, as a binary file does.

The extension itself still never runs git.

## Comments and Claude

- **Comments are untrusted text.** They are shown as text with a small formatting subset (paragraphs, bold, italics, code, lists, quotes), never as links or images; a code reference like `` `src/a.ts#L10-L20` `` is the one clickable form, and it goes through the same checks as code links. In the editor, comments are untrusted Markdown with HTML, commands and icons off and autolinks broken.
- **Only comments you send with Ask Claude go to Claude**, only to the Claude Code session you picked, with Sidestory's channel on. A plain comment, a teammate's comment, or any file in the repository never causes a push: what is pushed is decided by records in a per-user folder outside every repository (`~/Library/Application Support/sidestory` on macOS, `~/.local/state/sidestory` on Linux, `%LOCALAPPDATA%\sidestory` on Windows; created private, refused if it's a link or writable by others). Only your own words go in the push; everything else is ids and values that pass fixed patterns.
- **Other people's comments reach Claude only when it reads them**, through the plugin's tools, each labelled with who wrote it (`local_user` for your own, `claude` for this machine's Claude, `repository` for everything else) and escaped, under instructions that say they are data, not instructions. Who wrote a comment comes from a ledger in that same per-user folder, never from the name in the file; a file claiming to be Claude's that this machine didn't write shows as "Claude (from the repository)".
- **The channel can't approve tool use** (it doesn't declare Claude Code's permission relay), listens on no port, and is a research-preview feature of Claude Code. Its reply tools only read and write thread files.
- **Local comments stay local:** `.sidestory/.local/` ignores itself through its own `.gitignore`, which is checked before every write; a repository that changes it gets no local comments.
- **Accepted risks:** Claude reading a teammate's comment can still be influenced by it; Claude's replies can be wrong or steered by what it read; any program running as you (including an agent) can send a comment to your Claude sessions, as it could already change your Claude Code settings or hooks.

## Interactive widgets

Widgets are React components in a sidestory's folder (`<explain-widget src="widgets/x.tsx">`). Unlike the rest of a sidestory, **they are code from the repository, and they run.** The boundary is your informed consent plus limits on what a widget can see; the sandbox makes misuse harder but is not treated as containment.

### When widgets run

- Never in Restricted Mode (an untrusted workspace), and never while the `sidestory.widgets.enabled` setting is off. The setting is application-scoped: a repository's `.vscode/settings.json` can't turn it on.
- Only after you agree in a **native VS Code dialog** (not in the panel, whose content the sidestory controls). It names the sidestory and its changed files, and says that widgets can read the code the sidestory points at, including unsaved edits, and may be able to reach the network (their usual network calls fail, but the sandbox is best effort, below). When the widgets would also read anchors whose quotes nobody confirmed, the same dialog lists those files and line ranges and offers to allow both at once; "Run Widgets" alone allows only running.
- Each sidestory asks the first time its widgets would run in a workspace, with or without git (a sidestory copied or unzipped into a workspace you trusted doesn't run on another sidestory's consent).
- Consent is kept per workspace (VS Code's workspace storage; in browser VS Code that storage is per browser profile), with a hash of every file each sidestory's widgets load (code, JSON, images) and the blob git had for it at HEAD. The last 16 versions of each file you agreed to (or edited) are remembered with their git blob, so checking out a branch you already agreed to doesn't ask again; the same bytes under another blob still do. You're asked again when widget code changes after git's own version of that file changed (a checkout, pull, merge or rebase), whatever the working-tree bytes look like (line-ending conversion, checkout filters such as `ident` or LFS, encodings), and for widget files you never agreed to that git has (another sidestory's widgets after a clone or pull). The decision waits until git has finished (no index lock, no merge or rebase in progress) and for a status refresh made after the change. You're always asked about changed code when the folder is in a git repository VS Code's git extension doesn't know, when git doesn't settle, or when a widget file is reached through a symlink anywhere below the repository root (the file, a folder, the sidestory folder or `.sidestory` itself). Edits in the working tree, by you or by any tool, are treated as yours and don't re-ask. **Sidestory: Revoke Widget Consent** clears it, together with the anchors you let widgets read.
- All of this is enforced by the extension host: the panel gets no compiled code, libraries or file contents for widgets without trust, the setting and consent.

### What a widget can reach

- **Its own frame.** Each widget runs in an `<iframe sandbox="allow-scripts">` with an opaque origin, created by the panel and laid over the sidestory. It can't reach the panel's document, VS Code, other widgets, the file system or VS Code's resource URLs. The frame's CSP allows only the bootstrap script (by hash) and what it loads, inline styles, and `data:`/`blob:` images, fonts and media; `eval`, popups, dialogs, form submission and navigation of other frames are blocked. `fetch`, XHR, WebSocket, EventSource and `sendBeacon` are replaced with stubs that refuse, and WebRTC constructors and `<link rel=prefetch|preconnect|dns-prefetch|prerender|modulepreload>` are removed inside the frame. That last hardening is best effort: a widget can create a scriptless child frame whose constructors are unpatched.
- **Code, only when its author demonstrably knew it.** `useAnchorCode` returns an anchor's code only when the anchor's pinned quote (whitespace-normalized, case-sensitive) is committed in git or was confirmed by you in VS Code, the code matches it in full (or, for files tracked by git, the quote matches the committed version and the differences are working-tree edits), the file isn't ignored by git, isn't secret-looking (below), and is at most 2,000 lines. Git state comes from VS Code's git extension; the extension never runs git itself. Git is asked about the file the code is read from (behind any symlink). A widget gets the code only of anchors it names in a direct `useAnchorCode('id')` call (any anchor when the id is computed or the function is used any other way), however it asks. Pinning anchors that widgets read asks you first (a native dialog listing the files and line ranges), unless the quote stays as it is committed; the standalone checker refuses to pin them unless given `--yes-widgets-may-read`.
- **Files it imports** from the sidestory folder only (real paths checked, sizes capped, the same secret-file names refused). Each widget gets only its own props, state and code.
- **Secret-looking files, never.** No widget gets a file whose *name* looks like it holds secrets: not through `useAnchorCode`, not as an import or image. The rule is judged on the file name (the last path segment), case-insensitively, against both the path the sidestory names and the real file behind any symlink; folder names don't count. Secret-looking, whatever the extension: `.env`, `.env.*`, `.envrc`; `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.keystore`, `*.jks`, `*.tfvars`; names containing `kubeconfig`; `id_rsa`, `id_dsa`, `id_ecdsa`, `id_ed25519` and their `.pub`; `.npmrc`, `.netrc`, `.pypirc`, `.git-credentials`, `.dockercfg`, `.htpasswd`; `appsettings.*.json`. Secret-looking only for config and data files (extension `json`, `yaml`, `yml`, `toml`, `ini`, `env`, `conf`, `cfg`, `properties`, `xml`, `txt`, or none): names containing `secret`, `credential`, `password`, `token`, `apikey` (also `api-key`, `api_key`), or `.local.` (`settings.local.json`). Source files (`.ts`, `.tsx`, `.js`, `.py`, `.sv`, `.go` and every other extension) are never secret by name, so `src/tokenBucket.ts` or `src/tokens/lexer.ts` can be read like any code; a secret kept in a source file, or in a file not on this list, is protected only by the other rules (the quote must be author knowledge, ignored files are never served, and you consent to the widgets).
- **The editor, within limits.** A widget can highlight lines inside the current step's code without a click. Showing code, changing steps and moving focus need a click or key press in that widget, checked by the panel when the request arrives (user activation, the widget's frame holding focus, and no gesture of the panel's own that pointed elsewhere). Only the part of a widget you can see counts as where the pointer pointed. A widget's frame never extends past its placeholder, whose size author CSS can't change, and the panel draws the "Interactive" label over a running widget itself, outside the sidestory's content, so author CSS can't hide it. Requests are schema-checked, size-capped and rate-limited.
- **Resources.** Widget code is compiled in a worker thread with time and memory limits. In the frame, loops are guarded (stopped after about 1 s without yielding), a watchdog unmounts and disables a widget that stops answering, and at most 8 widgets are mounted at once (24 per sidestory). The watchdog acts on the panel's own evidence (pongs missing while the panel's timers run on time; heartbeats that come back late by the panel's clock, or stay missing for 20 s) and never while one of the extension's dialogs is open or for 5 s after (VS Code holds a webview's messages back behind its dialogs). A widget it turned off offers **Try again** in its box, which counts toward stopping the sidestory's widgets (a third hang within 5 minutes stops them until **Sidestory: Enable Widgets**).
- **Focus.** A widget never gets focus without your interaction: focus that arrives without evidence of your click or key press in that widget is given back, every time. A widget that keeps doing it is stopped after three attempts the panel is sure of; its box offers **Restart widget**. Attempts the panel isn't sure of aren't counted: the pointer resting on the widget, or the widget's frame reporting a pointer or key press of its own at that moment (an instant click by automation or assistive technology, which shows the panel no pointer travel). That report comes from the widget's frame, so a hostile widget can make itself exempt from being stopped this way, but not from having focus taken back; focus pulled from outside the webview (the editor) always counts.
- **Stored data.** What readers set in widgets (`useWidgetState`, at most 64 KB per widget and 256 KB per sidestory, 16 sidestories) is kept in the workspace storage of VS Code, as the panel's own state is; it holds only what widget code chose to save.

### Accepted risks

These are known and accepted; they are why running widgets needs your consent.

- **Widgets may reach the network.** WebRTC, prefetch-style links and future browser features can get past the frame's CSP; the hardening above reduces casual misuse but isn't complete. Treat anything a widget can see (its props, its state, the code `useAnchorCode` gives it) as something it could send out.
- **Deceptive UI inside the widget's box.** A widget can draw anything in its box, which the panel frames and labels "Interactive", including a fake cursor drawn while the real pointer is inside it.
- **Clipboard writes and drag-out data** after a click in the widget (pastejacking): check what you paste.
- **Focus theft from the editor.** A widget that takes focus without a click can receive up to about 200 ms of keystrokes before the panel notices and gives focus back.
- **Pointer-based allowances.** Within about 5 s of pressing J or clicking a panel control, a widget the pointer moves toward (or across, on the way out of the panel) can navigate or take focus; refusing it would break "press J, then click the widget that came up". So can a widget the pointer was already resting on, or had just moved into (heading in, within about 24 px of its edge), when a key was pressed in the panel; not one that moved or grew under a pointer resting elsewhere.
- **Between widgets.** A widget can take focus within about 5 s of a click inside another widget: the panel sees neither click.
- **Touch.** With no pointer samples, a tap on the prose followed within about 5 s by a tap on a widget is refused; tap again.
- **Fast moves.** After a fast pointer move into a widget and a key press in the panel, a click in that widget within about 5 s may be refused (focus returns to its placeholder); click again. It never counts against the widget.
- **Refocus target.** After a focus theft, focus returns to the active editor group, even if it was taken from the terminal or the sidebar.
- **Keyboard.** Escape and Tab are seen by widget code first, so a widget can hold keyboard focus until you click elsewhere. VS Code shortcuts don't work while focus is in a widget.
- **Side channels** between widgets and the panel in the shared renderer process (timing, memory pressure).
- **Unsaved edits.** `useAnchorCode` serves the live text of a resolved anchor, unsaved edits included (the consent dialog says so).
- **Consent follows the working tree.** Widget code changed by any tool, including other extensions or agents writing files, counts as your own edit and doesn't re-ask. Code that arrives without HEAD moving (`git checkout <rev> -- path`, `git restore --source`, `git apply` of a pull request's diff, `git stash pop`) doesn't re-ask either, once the sidestory's widgets have run here; a whole sidestory copied or unzipped in asks the first time. Without git, changes to a sidestory you agreed to don't ask again. The limits on what widgets can see apply regardless.
- **Panel origin.** The panel accepts host messages only from its own origin, which relies on that origin being shared only by this extension's panels, which run only its own script.
- **Hangs.** A widget that hangs freezes the other widgets (they share one process). Where sandboxed frames aren't isolated in their own process, it also freezes the panel, and in a browser without site isolation (possible when VS Code runs in a browser) the whole VS Code tab, until the watchdog disposes the panel and recreates it with that widget disabled. VS Code desktop keeps site isolation on, so there a runaway widget can't freeze the window.
