Flushing makes writes cheap and reads slower: every flush adds a table a get might have to check. Compaction pays that debt back (inline here, on background threads in real stores), merging tables into fewer, larger, non-overlapping ones, and throwing away what has been overwritten or deleted.

The shape it maintains

L0 is a pile of flushed memtables, each sorted but overlapping the others. From L1 down, each level is one sorted run cut into tables: no two overlap, so a get checks one table per level. Each level may hold level_multiplier times more than the one above, so a few levels cover a lot of data, and most of it sits in the last.

Watch compaction keep up

Write batches of four writes (about a memtable's worth) and step through the events: a flush adds a table to L0; at three, L0 is merged into L1; when L1 outgrows its limit, one of its tables is merged into L2. The editor shows the line that decides or does each step.

As writes continue, L0 fills again every three flushes, L1 grows past 320 bytes and hands tables down to L2, one at a time, round robin through the key space. Each byte you write is flushed once and then rewritten by every compaction it takes part in: the write amplification, about 3 after forty batches here.

pick: L0 first, then the first over-full level

L0 is checked first: its tables slow every get. Then each level from L1 down, against its byte limit. For an over-full level it takes one table at a time, until the level is back under its limit, and next_key remembers where the last one ended so the next compaction takes the following table: over time, every key range gets pushed down evenly.

The inputs always include every table of the next level that overlaps: that is what keeps the next level free of overlaps.

run: merge, newest wins, cut into tables

for key, value in merge(t.items() for t in c.inputs + c.overlaps):  # newest first
    if value is None and not self._deeper_may_hold(out, key):
        continue  # a tombstone with nothing left to hide
    if builder is None:
        builder = TableBuilder(self.levels.table_path(), …)
    builder.add(key, value)
    if builder.size >= self.opts.table_bytes:
        outputs.append(builder.finish())

Inputs are listed newest first (L0's tables newest first, then the next level, which is older), so the merge keeps each key's newest entry and drops the rest: overwritten values die here. The output is cut every table_bytes, at any key, since keys are unique and sorted.

When a tombstone may go

A tombstone exists to hide older values of its key. Older values only ever live deeper, so once a tombstone is being written to a level below which no table's range covers its key, there is nothing left to hide, and it is dropped. Until then it must be kept, even though the merge just consumed the values it was hiding in these inputs: a deeper level may hold another.

Dropping a tombstone too early resurrects deleted data: the old value below becomes the newest again. tests.py checks exactly that.

The swap: one commit, then delete

The new tables are complete and synced before anything changes. Then the level lists are updated in memory and the manifest is committed: one atomic rename. Only after that are the input files deleted. A crash at any point leaves either the old tables or the new ones as the database, never a mix; the losers are debris that the next open removes.

A scan that started before the swap may still be reading an input table: it holds the open file, and on POSIX a deleted file stays readable until its last handle is closed.

The price: write amplification

Each byte is written to the log, flushed once, and then rewritten every time it moves down a level, and often more: merging one table into the next level rewrites the overlapping tables there too, about level_multiplier of them on average. Leveled compaction accepts that in exchange for reads that check one table per level and little wasted space. Tiered (size-tiered) compaction makes the opposite trade: fewer rewrites, more overlapping tables to read.
