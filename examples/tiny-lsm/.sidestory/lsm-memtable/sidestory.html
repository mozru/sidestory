The memtable is where every write lands, and the first place every read looks. It has to answer two questions fast: "what is the newest value of this key?" for gets, and "what are the keys in order?" for flushes and scans.

A dict for lookups, a sorted list for order

Neither alone does both jobs. A dict finds a key in O(1) but has no key order; a sorted list has the order but its lookups are a binary search. So the memtable keeps both: _values maps each key to its newest value, and _keys holds the same keys, kept sorted.

put: insert once, overwrite in place

A key seen for the first time is inserted into _keys with bisect.insort: a binary search for the spot, then a shift of everything after it. A key seen before only changes its value in the dict: the memtable keeps only the newest version: an older one could never be read anyway.

size counts what the entries will take once encoded (a 7-byte header, the key, the value), so the flush threshold roughly measures the data the new table will hold (its CRCs, index, bloom filter and footer come on top).

insort's shift is O(n) per new key, which is fine for a memtable of a few thousand entries in a teaching store. LevelDB and RocksDB use a skip list instead: O(log n) inserts that also allow concurrent readers.

Three answers, not two

A get can't stop at "not here": an older value may be in a table below. So get distinguishes three answers, and DB.get keeps looking only on the third:

MISSING is a one-member enum, so a type checker can tell it apart from bytes and None.

items: a range, and a copy

Two binary searches find the slice of _keys in [start, end). The result is a new list, not a view: a scan iterating it isn't disturbed by writes that arrive meanwhile (or by a flush replacing the memtable), so it sees the database as it was when the scan began.

lo = 0 if start is None else bisect.bisect_left(self._keys, start)
hi = len(self._keys) if end is None else bisect.bisect_left(self._keys, end)
return [(key, self._values[key]) for key in self._keys[lo:hi]]

When it's full

After every write, _write compares size with memtable_bytes (64 KB by default). A bigger memtable means fewer, larger L0 tables and less compaction, but more memory, and more log to replay after a crash.
