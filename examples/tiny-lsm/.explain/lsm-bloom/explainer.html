A get that misses the memtable may have to ask every L0 table and one table per level. Most of them don't have the key. A bloom filter lets each table say so from memory, in a few bit tests, so a get reads about one block no matter how many tables it passes.

Bits that can only say "no" for sure

Adding a key sets k bits of an m-bit array. A lookup checks the same k bits: if any is 0, the key was never added, guaranteed. If all are 1, the key was probably added, or other keys happened to set all its bits: a false positive. There are no false negatives, which is the property a read path needs: a filter may waste a read, never miss a value.

One 64-bit hash

FNV-1a is a few lines and fast, but similar keys (key00041, key00042) come out with similar bits. MurmurHash3's finalizer (shift, multiply, shift, multiply, shift) mixes every input bit into every output bit; without it, a table of 500 such keys (every other number) answered "maybe" for 5–6% of the numbers in between instead of 1%.

k positions from two halves

Computing k separate hashes would be slow. Double hashing takes the hash's low half as a start and its high half as a step: (h1 + i·h2) mod m for i = 0…k−1, which in theory and practice is as good as k independent hashes. Add keys, look some up, and change m and k; the editor follows add and might_contain.

With 48 bits and 3 hashes, apple, banana and cherry set up to 9 bits. A lookup of a key that was never added almost always finds a 0 among its 3 bits: the formula (1 − e−kn/m)k gives about 0.5% false positives. With twelve keys in the same 48 bits it is about 15%.

Sizing: bits per key, and the best k

for_keys gives every table bits_per_key bits per key (10) and k = round(bits_per_key · ln 2), the k that minimises false positives. More hashes set more bits; fewer hashes check fewer; ln 2 is where the array ends up about half full.
