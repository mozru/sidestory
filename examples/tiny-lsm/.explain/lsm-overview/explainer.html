A key-value store in under 900 lines of Python that never updates anything in place. Writes land in a log and a sorted in-memory table; full tables are written out once, never changed, and merged together as they pile up. Reads pay for that by looking in several places, newest first. Read this page for the shape of the whole; dive into a component only when you need it.

The store at a glance

Data moves one way: from the write path at the top left (a put is logged, then inserted into the memtable) down into ever larger levels of immutable SSTables on the right. Reads walk the same structure in the other order: the memtable first, then L0's tables newest first, then one table per deeper level. Compaction keeps the levels few and sorted, and the MANIFEST records which files make up the database.

Reading the wires: thick = entries being written, green = lookups and results, dashed = control (commits, triggers), dotted = recovery on open. Click a block to see its code.

wal.py

Every write is appended, with a CRC, before anything else sees it. Replayed after a crash.

memtable.py

The newest writes, sorted, in memory. Deletes are stored as tombstones.

sstable.py

Immutable sorted files: data blocks, a sparse index, a bloom filter, a footer.

bloom.py

A few bits per key that let a get skip most tables without reading them.

compaction.py

Merges L0 into L1, and each over-full level into the next; drops dead tombstones.

merge.py

A heap that merges sorted sources, newest entry per key: scans and compactions.

levels.py

The tables of each level, and the MANIFEST that names them, replaced atomically.

A put: log, memtable, and sometimes a flush

  1. Log. _write appends the entry to the write-ahead log first: once that returns, the write survives the process crashing (and with sync=True, a power cut).
  2. Insert. Then it goes into the memtable, where the next get will find it. A delete is the same write with no value: a tombstone.
  3. Flush. When the memtable reaches memtable_bytes, flush writes it out, already sorted, as one new L0 SSTable, commits the manifest, and starts an empty memtable and a fresh log; the old log is deleted, its writes now safe in the table.
def _write(self, key: bytes, value: Value) -> None:
    self._wal.append(key, value)  # durable first,
    self._mem.put(key, value)  # then visible
    if self._mem.size >= self.opts.memtable_bytes:
        self.flush()

A put never reads a table or changes one in place: that is where an LSM tree gets its write speed. (Here the put that fills the memtable also flushes and compacts before it returns; real stores do both on background threads.) Without the simulation: 23 puts and a delete. Every fourth put or so fills the 48-byte memtable, which is flushed as a new L0 table. The third L0 table triggers a compaction into L1, and L1, now over its 320-byte limit, pushes a table down to L2.

Compaction: merging down

Every flush adds a table to L0, and a get must check every L0 table, so L0 has to be emptied. pick chooses the work; run does it:

triggerinputsoutput
L0 has l0_limit tablesall of L0, plus the L1 tables they overlapnew L1 tables
Ln holds more than its limitone Ln table (round robin), plus the Ln+1 tables it overlapsnew Ln+1 tables

The inputs are merged, newest entry per key, into new tables of about table_bytes; one manifest commit swaps them in. Because every overlapping table takes part, L1 and below stay sorted with no overlaps, so a get needs only one table per level. A tombstone is dropped once no deeper level can hold its key.

Control in focus: a flush commits the manifest and may trigger compaction, which merges a level into the next and commits again.

A get: newest first, stop at the first hit

The newest value of a key is in the first place that has any entry for it, so get looks newest first and stops there, even when what it finds is a tombstone:

  1. the memtable;
  2. every L0 table, newest first (their ranges overlap);
  3. in each deeper level, only the one table whose key range covers the key.

A table that can't hold the key costs no disk read: its key range and its bloom filter are in memory. Only a "maybe" from the filter reads a block, and one block at most.

Without the simulation: get(cherry) stops in the memtable; get(apple) stops at the newest L0 table; get(kiwi) skips one L0 table by its bloom filter and finds a tombstone in the next: deleted; get(fig) passes both L0 tables on their bloom filters, skips L1 by range and finds fig in L2; get(lime) is turned away by three bloom filters and L2's key range, without a single block read.

A scan: merge every source

A range can't stop at the first hit: its keys are spread over the memtable and every table that overlaps it. scan takes a snapshot of the memtable's range and one iterator per overlapping table, newest first, and merge yields their entries in key order through a heap, keeping the newest entry per key; live then drops tombstones. Bloom filters don't help here: they answer "is this key here?", not "which keys are in this range?".

Without the simulation: scan(c, m) merges five sources (the memtable, two L0 tables, one L1 and one L2 table). cherry and date come from the newest sources, shadowing older entries; kiwi's newest entry is a tombstone, so it is skipped; the result is cherry, date, fig, grape, lemon.

Recovery: the manifest, then the log

Opening a database is crash recovery, every time. Levels.load reads the MANIFEST, opens the tables it names and deletes any file it doesn't (debris of a flush or compaction that never committed). Then the live log, the one the manifest names, is replayed into a fresh memtable: exactly the writes that weren't flushed yet.
