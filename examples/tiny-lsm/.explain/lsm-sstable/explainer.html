An SSTable (sorted string table) is a memtable frozen to disk: entries in key order, written once and never changed. Its shape is chosen so a reader can find any key with one disk read, after keeping a few kilobytes of it in memory: the index and the bloom filter.

The file, byte by byte

A real table written by tiny_lsm (nine fruits, block_bytes=48): data blocks first, then the index, the bloom filter and a footer. Everything a reader needs to find its way is at the end, because only when the last block is written does the writer know where the blocks are.

Writing: cut a block every block_bytes

add appends encoded entries to the current block and refuses keys out of order: sorted input is the whole point. When a block holds block_bytes (4 KB by default), _finish_block appends a CRC32, writes it out, and fills in the index entry it opened with the block's first key.

A block is the unit of reading: big enough that one disk read fetches many neighbouring keys, small enough that a point lookup doesn't read much it doesn't need.

finish: index, bloom filter, footer, fsync

index_offset, bloom_offset = self._offset, self._offset + len(index)
footer = FOOTER.pack(index_offset, len(index), bloom_offset, len(bloom), len(self._keys), MAGIC)
self._file.write(index + bloom + footer)
self._file.flush()
os.fsync(self._file.fileno())  # durable before the manifest may name it

The index is sparse: one entry per block, not per key, so it stays small enough to keep in memory. It ends with the table's last key, so the table knows its key range (first key of block 0 to last key) without reading a block. The fsync matters: the manifest will soon name this file, and a name must never point at bytes still in a cache.

Opening: read from the end

  1. Seek to the end: the last 40 bytes are the footer. A wrong magic means this isn't a table.
  2. The footer gives the index's offset and size: read it, decode first keys and block positions.
  3. The same for the bloom filter.

Three reads, once per table. From then on, min_key, max_key, the first keys and the filter live in memory; blocks stay on disk.

The block search relies on the keys being sorted: the block whose first key is the last one ≤ key is the only place it can be. Scanning inside the block stops early at the first larger key.

items: a range, one block at a time

A scan starts at the block that may hold start, skips the keys before it, and stops at the first key ≥ end. It's a generator: blocks are read only as the merge asks for more, so a scan that's abandoned after ten keys reads one or two blocks of each table, not the whole table.

Every block is checked

A block that fails its CRC raises CorruptionError instead of returning wrong data. Unlike the log, a table is never truncated or repaired: it was complete when the manifest named it, so damage is a disk fault, and the right response is to stop and say so.
