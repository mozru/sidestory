The memtable lives in memory, so a crash loses it. The write-ahead log is how it comes back: every write is appended to a file before anything else happens, and replaying that file rebuilds exactly the writes that hadn't reached an SSTable yet.

A record: a checksum, a length, an entry

The entry is the same bytes an SSTable stores (encode_entry); the log only adds a length, so replay knows where the record ends, and a CRC32 over length and entry, so it knows the record is whole.

A length that points past the end of the file is caught before the CRC is even computed. The CRC covers the length too, so a damaged length that points somewhere inside the file isn't believed either.

tiny_lsm always flushes; it fsyncs only with Options(sync=True) (and then also syncs the directory when it creates a log, so the file's name survives too), because an fsync costs milliseconds per write. Real stores amortize it by syncing a batch of writes at once (group commit).

Replay: trust records until one fails

A crash mid-append leaves the last record short. replay walks records from the start and stops at the first one that runs past the end of the file or fails its CRC; then it truncates the file there, so the next append starts on a clean boundary. Pick a crash:

All three records check out: the memtable gets apple, fig and kiwi's tombstone. Nothing is cut.
Fewer than 8 bytes are left for record 3's header: the loop ends. Replay keeps records 1 and 2 and cuts the stray bytes. The delete was never acknowledged, so losing it is correct.
Record 3's length points past the end of the file: it is torn. Records 1 and 2 survive, record 3 is cut.
Record 2's bytes don't match its CRC. Replay stops there and cuts records 2 and 3, though record 3 itself is intact: after a bad record, the length that would find the next one can't be trusted.

Every open is a recovery

DB.__init__ doesn't know whether the last run ended cleanly, and doesn't need to. It loads the levels (the manifest), then replays the live log, the one the manifest names, into an empty memtable, and keeps appending to that same log. A clean shutdown and a crash take the same path.

log = self._levels.log_path()
if log.exists():
    entries, self.torn_bytes = wal.replay(log)
    for key, value in entries:
        self._mem.put(key, value)
self._wal = wal.WriteAheadLog(log, sync=opts.sync)

Which log is live

Logs and tables share one numbering. The manifest records log_number; a log with a smaller number was already flushed into a table, and _delete_debris removes it, together with any table the manifest doesn't name.

Rotation at a flush: the order matters

  1. The memtable is written as a table and synced (write_table).
  2. The manifest commits the table and the next log number, in one atomic rename.
  3. The new, empty log is opened; the old one is closed and deleted.

A crash before step 2 leaves an unnamed table (deleted on open) and the old log as the live one: its writes are replayed. A crash after step 2 leaves the old log as debris and a live log that may not exist yet: an empty memtable, which is right, because its writes are in the table.
